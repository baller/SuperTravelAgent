# SuperTravel 产品需求文档（PRD V2）

> 产品定义：以 Trip 为中心、由 Agent 驱动的旅行项目工作台  
> 版本：V2.0 Draft｜目标形态：单机 Web 完整演示版｜更新日期：2026-07-13

## 1. Executive Summary

### Problem Statement

用户在旅行前会收集大量零散攻略，却难以将其转化为满足时间、预算、同行人、开放时间和交通约束的可执行计划；旅行中条件持续变化，静态攻略又无法及时重排。多数 AI 旅行产品仍以一次性对话和长文本答案为中心，计划不可编辑、修改范围不可控、失败后无法恢复。

### Proposed Solution

SuperTravel 将一次旅行定义为持续演进的“旅行项目 Trip”，以结构化 `Trip State` 作为唯一事实源，以 `Trip Workspace` 承载计划、地图、预算、资料、冲突、版本和行中执行。聊天只是 Agent 读取和修改 Trip 的自然语言入口；所有修改先形成可预览的变更，再校验、应用并支持撤销。

产品主张：**把零散灵感变成真正能走、随时能改、改后仍可信的行程。**

### Success Criteria

- 新用户可在 8 分钟内完成“创建 Trip—导入灵感—生成行程—处理冲突—模拟变化—进入今日模式—导出”的完整演示。
- 20 个标准旅行场景中，至少 90% 可生成结构化行程；预置硬约束冲突检出率不低于 95%。
- 90% 的自然语言修改仅影响用户指定日期、地点或约束；锁定项目保护率为 100%。
- 所有 AI 修改均展示影响范围，100% 可预览、撤销和恢复历史版本。
- 工具异常、用户中断和信息不足场景中，系统均返回可继续操作的状态，不出现无反馈死循环。

## 2. User Experience & Functionality

### User Personas

核心用户是 18–35 岁、每年有 2–5 次自由行的年轻旅行者。他们习惯从社交平台、朋友分享和地图中收集攻略，愿意使用 AI 提效，但希望保留最终控制权。次要用户包括带父母或儿童出行、对节奏和可执行性要求更高的旅行者。

### Product Principles

1. **Trip 是产品，聊天是操作方式。** 对话不能成为计划的唯一存储位置。
2. **结构化状态优先。** 日期、地点、约束、费用和版本均进入明确的数据结构。
3. **AI 起草，用户决策。** 高影响操作必须先预览，不静默覆盖用户选择。
4. **先暴露不确定性。** 缺失信息、假设、数据来源和新鲜度应清晰可见。
5. **局部、可逆、可恢复。** 每次修改有作用域、有差异、有历史版本。
6. **完整主线优先。** 演示版先把单人旅行全生命周期做闭环，不堆叠社交和跨端功能。

### Information Architecture

- **首页**：新建旅行、导入灵感、最近 Trip、示例 Trip。
- **创建向导**：自然语言需求、结构化旅行卡片、关键澄清、约束确认。
- **灵感收件箱**：粘贴文本/链接、上传截图、POI 提取、去重、纠错、候选池。
- **Trip Workspace**：日程时间轴、地图、约束、冲突、预算、资料、Agent 和版本。
- **今日模式**：当前事项、下一站、交通、凭证、天气、完成/跳过、余程重排。
- **旅行回顾**：实际完成记录、费用总结、偏好反馈、可复用模板、游记式摘要。
- **导出中心**：可打印行程、Markdown/PDF、离线信息包。

### Core Object: Trip Workspace

桌面端采用三栏布局：左侧为日期、硬约束和完成度；中间为可编辑时间轴；右侧在地图、Agent、冲突和版本面板间切换。顶部始终显示目的地、日期、同行人、预算使用率、计划状态和最近保存时间。

每个 `ItineraryItem` 必须显示时间、地点、停留时长、预计费用、前往方式、开放/预约状态、推荐理由、来源与数据时间，并支持锁定、移动、替换、删除。交通段使用独立 `RouteLeg` 卡片，避免把“到达”和“游玩”混为一体。

### End-to-End Lifecycle

#### 旅前：从想法到可信计划

1. 用户输入：“十一带妈妈去苏州三天，预算 5000，不想太赶，必须去拙政园和平江路。”
2. Agent 生成 `TripSpec`，仅针对会显著改变方案的问题发起最多 3 个澄清；用户可跳过，系统记录显式假设。
3. 用户导入攻略文本、链接或截图。系统提取地点并展示证据片段、置信度、同名歧义和重复项，由用户加入、暂存或忽略。
4. 系统生成日程草案，规则引擎检查时间重叠、闭馆、路程、预算、每日强度和必去覆盖。
5. 用户通过拖拽、锁定或自然语言局部修改；Agent 展示变更前后差异与受影响范围。
6. 用户运行雨天、航班晚点、预算减少或体力下降等情景推演，确认后再应用。

#### 旅中：从静态计划到动态执行

- 今日模式只呈现当前最需要的信息，不要求用户阅读完整攻略。
- 用户可标记“完成”“跳过”“延迟”“临时加入”，实际状态与原计划分离记录。
- 当地点关闭、交通晚点或用户说“妈妈累了”时，Agent 先保留锁定项目与已完成项目，再重排未完成余程。
- 弱网或工具失败时展示最后可信计划；实时数据标记“暂不可用”，不清空已有日程。
- 用户可随时暂停生成、取消工具调用或继续上次未完成操作。

#### 旅后：从结束到可复用经验

- 自动汇总实际去过的地点、跳过原因、最终费用和计划偏差。
- 用户可对节奏、地点和推荐结果做轻量反馈，用于形成可查看、可编辑的偏好记忆。
- 支持将本次 Trip 复制为模板或导出回顾；演示版不建设公开内容社区。

### Differentiated Capabilities

- **旅行沙盘**：在应用前比较“原方案”和“变化后方案”，明确保留项、改动项与代价。
- **约束护栏**：将“必须去、不能早起、每天步行上限、预算”等从聊天文字提升为可验证规则。
- **可解释变更**：回答“为什么这样排”，并区分事实、推断、用户偏好和系统假设。
- **行中余程重排**：只调整尚未执行的部分，不破坏已完成、已预约或已锁定内容。
- **版本化旅行项目**：任何 AI 操作都产生 `PlanPatch`，而非直接重写整份行程。

### User Stories & Acceptance Criteria

#### Story 1：创建旅行

As a 旅行者，I want to 用一句话描述旅行 so that 我能快速获得结构化需求草案。

- 系统识别目的地、日期、同行人、预算、必去、禁忌和节奏；未识别字段明确为空。
- 仅当缺失信息会产生明显不同方案时提问，单轮不超过 3 个问题。
- 用户跳过澄清后仍可继续，所有假设显示在 TripSpec 中并可修改。

#### Story 2：导入零散攻略

As a 攻略收集者，I want to 导入文本、链接或截图 so that 我不用手工复制每个地点。

- 每个候选地点显示原始证据、提取置信度和来源。
- 同名地点要求确认；重复地点合并但保留全部来源。
- 单个素材解析失败不阻塞其他素材，支持重试或手工补录。

#### Story 3：生成并验证计划

As a 旅行者，I want to 得到按天、按时间排列的路线 so that 我能判断计划是否真的可走。

- 每个项目具有开始时间、时长、费用、交通段和推荐理由。
- 硬冲突标为“阻断”，风险标为“警告”，优化建议标为“建议”。
- 生成结果必须覆盖全部已确认的必去项，无法覆盖时说明原因并请求取舍。

#### Story 4：自然语言局部修改

As a 旅行者，I want to 说“第二天下午轻松一点” so that 我能低成本调整计划。

- 应用前显示新增、删除、移动及费用/时间变化。
- 未指定日期和锁定内容保持不变；作用域不明确时先确认。
- 应用后重新校验相关日期，并支持一步撤销。

#### Story 5：情景推演

As a 旅行者，I want to 模拟下雨或晚点 so that 我能提前准备备选方案。

- 推演不得直接修改主计划。
- 结果区分保留项、变更项、受影响约束和新增成本。
- 用户可选择应用全部、仅应用部分或放弃。

#### Story 6：旅中重排

As a 正在旅行的用户，I want to 处理突发变化 so that 剩余计划仍然可执行。

- 已完成、已预约和锁定项目默认不可移动。
- 重排只影响当前时间之后的项目，并给出放弃项及原因。
- 工具不可用时基于最近缓存给出保守方案并标记数据状态。

#### Story 7：中断与恢复

As a 用户，I want to 暂停或取消 Agent 操作 so that 我不会失去控制。

- 生成期间始终可见“停止”入口；取消后已提交的 Trip State 不回滚。
- 刷新页面后可恢复到最后检查点，并说明未完成步骤。
- 重复点击“应用”不会产生重复地点或重复版本。

#### Story 8：旅行回顾

As a 旅行者，I want to 记录实际体验 so that 下次规划更符合我的偏好。

- 计划项和实际完成项可对照查看。
- 偏好写入前向用户展示，允许编辑、拒绝和删除。
- 用户可复制 Trip 为新模板，原旅行保持只读归档。

### Global Experience States

每个主要界面必须设计正常、空、加载、部分成功、等待用户、取消、失败、离线/陈旧数据八类状态。Agent 不理解用户问题时，应提供当前 Trip 相关的可选动作；面对闲聊或无关问题可简短响应，但不得虚构行程修改。涉及删除整天行程、覆盖大量内容或降低硬约束的操作必须二次确认。

### Non-Goals

- 不做 iOS/Android 原生端、跨设备同步和实时多人协作。
- 不做社区信息流、达人内容生态或公开行程市场。
- 不接入真实支付、订票、退改和客服流程。
- 不承诺覆盖全球完整实时数据；演示数据必须清晰标识。
- 不向普通用户暴露模型、Agent 数量、MCP 或提示词配置。
- 不继承旧版以多 Agent 对话过程为卖点的产品结构；旧 React/FastAPI 仅可作为技术脚手架评估复用。

## 3. AI System Requirements

### Agent Operating Model

Agent 的任务不是输出一段漂亮攻略，而是安全地读取和变更 Trip。一次运行遵循以下闭环：

`输入规范化 → 意图识别 → 上下文装配 → 计划/工具选择 → 结构化结果 → 规则校验 → 变更预览 → 用户确认 → 状态提交 → 记忆候选`

系统只允许通过 `PlanPatch` 修改 Trip，不允许模型直接覆盖数据库对象。确定性规则负责时间、距离、预算、开放时间、锁定保护和版本提交；模型负责语言理解、素材抽取、候选生成、解释和方案比较。

### Intent Recognition

意图路由器至少识别：创建 Trip、补充需求、导入素材、事实查询、解释计划、局部修改、增加/删除、替换比较、冲突修复、情景模拟、旅中重排、撤销/恢复、暂停/取消/继续、导出、偏好管理、闲聊、无关请求和不支持请求。

- 输出必须包含 `intent`、`confidence`、`scope`、`entities`、`risk_level` 和 `needs_confirmation`。
- 低置信度且操作影响大时必须澄清；低风险事实查询可给出带假设的回答。
- 一个输入包含多个动作时，拆为有顺序的子任务，并在执行前展示摘要。
- “删掉下午安排”之类歧义请求必须绑定具体 Trip、日期和时间范围。

### Context Management

上下文按需装配，不把全部历史对话持续塞入模型：

- **Request Context**：本轮输入、当前页面、选中日期/卡片、用户操作。
- **Session Context**：最近对话摘要、尚未完成的 Agent Run、待确认问题。
- **Trip Context**：TripSpec、相关日期、约束、锁定项、当前版本和冲突。
- **User Context**：用户明确保存的稳定偏好，如步行耐受、饮食限制。
- **External Context**：工具返回的天气、开放时间、路线及其来源和时间戳。

上下文选择必须遵循最小充分原则。Token 预算不足时优先保留硬约束、当前作用域和未完成状态，压缩解释性历史；不得因为上下文截断遗失锁定项或用户明确禁忌。

### Memory Management

- **工作记忆**：当前运行中的步骤、工具结果和临时推理；运行结束后只保留摘要和审计信息。
- **Trip 记忆**：该次旅行的事实、决策、假设、版本和用户反馈，是主要持久记忆。
- **长期偏好记忆**：跨 Trip 的稳定偏好。只有用户明确陈述或多次行为一致时才形成“记忆候选”。
- **外部事实缓存**：带 TTL、来源和查询参数；过期数据不可伪装为实时事实。

长期记忆写入必须可见、可编辑、可删除。临时情绪、一次性预算和第三方敏感信息不得自动长期保存。当前输入与旧记忆冲突时，以当前输入为准，并提示用户是否更新偏好。

### Tool Requirements & Governance

演示版工具包括地点检索/地理编码、路线与耗时、开放时间、天气、公共交通、网页文本解析、截图 OCR、预算计算、行程规则校验、导出。允许真实 API 与固定数据混用，但必须统一通过工具适配层并标记 `live/mock/cached`。

每次调用均需具备参数 Schema 校验、权限声明、超时、有限重试、幂等键、结果大小限制、来源记录和取消信号。只对网络抖动、限流等可恢复错误重试，并采用退避；参数错误和权限错误不得盲目重试。高频失败工具进入短时熔断，系统回退到缓存、替代工具或手工输入。

网页和攻略内容属于不可信输入，不得把其中指令当作系统命令。工具结果在写入 Trip 前必须转换为统一结构并通过规则校验；同一运行中相同参数优先复用结果，避免重复调用和成本失控。

### Interruption, Concurrency & Failure Management

- 每个 Agent Run 具有 `run_id`、状态、检查点和取消令牌；状态为 `QUEUED/RUNNING/WAITING_USER/PARTIAL/SUCCEEDED/CANCELLED/FAILED`。
- 用户新输入与进行中任务冲突时，先判断是补充、替换还是独立查询；替换操作取消旧运行，补充信息合并至待确认步骤。
- 同一 Trip 同时只能提交一个写操作。若基础版本已变化，系统重新计算 Patch 或要求用户选择，不静默覆盖。
- 工具部分成功时保留已验证结果并生成 `PARTIAL` 状态；界面说明缺失内容和继续方式。
- 输出解析失败先进行一次受约束修复，仍失败则回退为安全说明，不把半结构化内容写入 Trip。
- 达到最大循环次数、时间或成本预算后停止，返回当前进度和可恢复检查点。
- 未知异常统一生成可追踪错误编号；用户看到的是影响、已保留内容和下一步，而不是堆栈信息。

### Human-in-the-Loop Rules

以下操作必须确认：删除整天或多个锁定项、改变目的地/日期/同行人、突破预算硬上限、用陈旧数据替代关键实时信息、应用影响多个日期的推演结果。普通拖拽、补充备注和低风险局部调整可直接执行，但仍产生版本。

### Evaluation Strategy

建立至少 30 个固定测试场景，覆盖信息缺失、同名地点、预算冲突、闭馆、跨城路程过长、老人同行、雨天、航班晚点、工具超时、限流、解析失败、取消、重复提交、锁定保护、局部修改、并发冲突、回滚、离题问题和恶意网页指令。

核心指标包括：意图准确率、实体抽取 F1、硬约束满足率、冲突召回率、POI 事实准确率、修改作用域准确率、工具成功率/重复调用率、平均澄清次数、首个可用结果时间、取消生效时间、恢复成功率、撤销成功率和单次运行成本。发布门槛为关键路径用例 100% 通过、总体场景通过率不低于 90%，且不存在锁定项被静默删除的案例。

## 4. Technical Specifications

### Architecture Overview

```text
Web Client
  ├─ Trip Workspace / Today / Review
  ├─ Chat Command Bar / Change Preview
  └─ Local View State
            │
Trip API + Agent Runtime
  ├─ Intent Router & Context Builder
  ├─ Run Manager / Checkpoint / Cancellation
  ├─ Planner & PlanPatch Generator
  ├─ Tool Gateway / Cache / Circuit Breaker
  └─ Deterministic Validator
            │
Trip Store + Version Store + Memory Store + Run/Event Log
            │
Map / Place / Weather / Parser / OCR / Export adapters
```

前端界面只渲染结构化 Trip 和运行事件；模型文本不能直接成为行程卡片。后端以单体服务和本地数据库即可完成演示，技术栈可继续使用 React、FastAPI 与 SQLite，但产品逻辑不受旧版顺序式多 Agent 架构约束。

### Core Data Model

- `Trip`：身份、名称、生命周期状态、当前版本。
- `TripSpec`：目的地、日期、同行人、预算、节奏、必去、禁忌、假设。
- `TripDay` / `ItineraryItem` / `RouteLeg`：日程与交通结构。
- `Place` / `SourceClip`：标准地点与素材证据。
- `Constraint` / `Conflict`：可校验规则、严重度、修复建议。
- `Booking` / `Expense`：预约凭证和计划/实际费用。
- `Scenario`：假设条件及模拟结果，不直接修改主计划。
- `PlanVersion` / `PlanPatch`：版本快照、变更集、作者、原因和基础版本。
- `AgentRun` / `ToolCall`：运行状态、检查点、错误和审计事件。
- `UserPreference`：来源、置信度、更新时间和用户确认状态。

### State Machines

Trip 生命周期：

`DRAFT → COLLECTING → PLANNING → REVIEWING → READY → IN_TRIP → COMPLETED → ARCHIVED`

任何阶段可保存草稿；规划任务的异常状态不直接改变 Trip 生命周期。Agent Run 使用独立状态机，并通过检查点恢复。只有已验证且用户授权的 Patch 才能推进 Trip 版本。

### Integration Points

- 地图、地点、路线、天气等第三方服务通过统一 Adapter 接入，便于真实和 Mock 数据切换。
- 链接解析和 OCR 只返回素材候选，不直接写入日程。
- 演示版不要求完整登录系统，可使用本地单用户身份；导出支持 Markdown 和 PDF。
- API 需覆盖 Trip CRUD、素材导入、生成/模拟、Patch 预览与应用、版本恢复、Run 取消/继续及事件流。

### Observability

每次运行记录意图、选取上下文、模型/工具耗时、重试、校验结果、Patch、用户确认和最终状态。开发者调试页可按 `trip_id/run_id` 查看时间线和脱敏输入输出；面向用户的界面只展示进度、影响和恢复建议。日志不得记录 API Key、完整票证图片或未经脱敏的敏感文本。

### Security & Privacy

- API Key 仅由服务端环境配置，禁止通过公开接口写入或在前端展示。
- 上传图片默认仅用于当前 Trip，支持一键删除；演示版不采集身份证、护照等高敏信息。
- 外部网页文本按不可信数据处理，防止提示词注入和工具越权。
- 导出文件提示可能包含个人行程信息；用户可清除 Trip、上传资料和长期偏好。
- 所有工具采用最小权限；具有写入或高成本行为的工具需显式授权与限额。

## 5. Risks & Roadmap

### Phased Rollout

#### MVP：完整可演示闭环

- 全新首页、创建向导、TripSpec 和示例 Trip。
- 文本/截图导入、POI 提取确认、去重和候选池。
- Trip Workspace：按天时间轴、地图、交通段、拖拽、锁定、预算概览。
- 规则冲突中心、Agent 局部修改、变更预览、版本撤销。
- 至少四种情景推演：雨天、晚点、预算降低、体力下降。
- 今日模式：完成/跳过/延迟、余程重排和缓存数据提示。
- 旅行回顾、偏好候选、Trip 复制、Markdown/PDF 导出。
- 完整的加载、部分成功、取消、失败、恢复状态；30 个固定评测场景。

MVP 可使用“苏州三日游”等高质量城市数据集和可控工具 Mock，但所有核心交互必须真实生效，不能仅做静态页面或预录动画。

#### v1.1：增强旅行执行

- 酒店、交通、门票凭证卡片与截图识别。
- 计划/实际预算明细、行李和预约清单。
- 更丰富的地点替换对比、更多城市数据集和离线包。
- 面向开发的 Agent 运行看板与自动回归评测。

#### v2.0：概念储备，暂不实现

- 多人协作、跨端同步、真实预订、公开模板市场、通知服务。
- 在获得足够用户反馈后，再评估更复杂的长期记忆和个性化推荐。

### Technical & Product Risks

- **范围膨胀**：以 5–8 分钟主演示脚本作为取舍标准，非主线功能不进入 MVP。
- **AI 输出好看但不可执行**：结构化输出后必须经过确定性规则校验，校验未通过不可标记为“就绪”。
- **第三方数据不稳定**：Adapter、缓存、Mock、超时和降级路径必须同时存在并可在界面识别。
- **修改不透明导致不信任**：任何 Agent 写操作均以 Patch 预览和版本历史呈现。
- **长会话状态漂移**：以 Trip State 而非聊天历史恢复上下文，关键约束进入固定上下文层。
- **演示过度依赖理想输入**：评测和演示必须包含缺失信息、打断、工具失败及临时变更。

### Canonical Demo Script

用户创建“带妈妈去苏州三天”的 Trip，导入两段攻略和一张截图；系统提取并合并重复 POI，用户确认必去项后生成计划。冲突中心发现闭馆时间和步行过量，用户锁定拙政园与平江路，再输入“第二天下雨，而且妈妈累了”。旅行沙盘展示保留项、替换项和费用变化，用户仅应用第二天方案并查看版本差异。随后进入今日模式，标记一处景点跳过并重排余程，最后查看实际行程与预算、保存节奏偏好并导出 PDF。

该脚本必须同时证明四件事：**Trip 是事实中心、Agent 修改可控、现实变化可恢复、完整生命周期有闭环。**
